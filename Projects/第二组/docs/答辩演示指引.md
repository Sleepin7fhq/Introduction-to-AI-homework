## 📋 演示流程（按顺序讲）

### 【第 1 幕】系统架构 —— 1 分钟

**话术**：

> "这个系统分两层：**C++ 核心推理内核**和**Gradio UI 外壳**。
> 内核负责音频采集、梅尔频谱提取、ONNX 推理、时长统计、阈值判断；
> UI 只做展示和配置，**完全不碰音频原始流，也不做任何推理**。
> 两层之间用本地回环 socket 通信，协议是 JSON 行，UI 只能拿到结构化结果。"

**动作**：打开 `kernel/` 目录，指一下 `include/dn/` 下的 8 个头文件。

```
kernel/src/     7 个 .cpp：采集、特征、推理、流水线、IPC、WAV、main
kernel/include/ 8 个 .h  ：对外数据结构都在 types.h
ui/             2 个 .py  ：app.py（界面）+ kernel_client.py（IPC 客户端）
```

**补充话术（如果被追问"两个进程怎么同步"）**：

> "IPC 用的是 **JSON-lines + 请求/响应配对（rid）**：
> UI 每发一条命令就带一个唯一 `rid`，内核把 `rid` 原样回填到响应里；
> 同时内核每 500 ms 会主动广播一条 `type=state` 的快照。
> UI 端按 `rid` 把响应交给对应的等待者，广播进另一个队列 ——
> 所以**命令响应不会被周期性广播挤掉**。"

```powershell
# 现场可验证：响应里带 rid
.\build\bin\dorm_noise_kernel.exe --port 8765
# 另开一个终端
#   {"cmd":"status","rid":"a1b2c3d4"}   →  {"type":"state",...,"rid":"a1b2c3d4"}
```

### 【第 3 幕】离线推理 —— 1.5 分钟（**最稳妥的演示**）

**动作**：UI → 「🎧 离线文件推理（答辩演示）」Tab。

当前四类为 **大声喧哗 / 正常音量 / 游戏外放 / 正常交谈**（key 顺序 `loud_talk / normal_volume / game_audio / normal_talk`），默认累计时长阈值 **[15, 9999, 45, 9999] 秒**。

演示前用新版内核逐项预检并记录实际输出，不沿用旧版置信度：

| 顺序 | 素材 / 操作 | 验证目标 | 现场解读 |
|---|---|---|---|
| 1 | `real_speech_0.wav` | 高于门限时，真实朗读应为正常交谈，top 标签 Speech | “这是实际人声交谈语义验证，记录本次置信度与 RMS” |
| 2 | 低电平片段或降低输入增益，使每段 RMS ≤ -45 dBFS | 正常音量 | “低电平优先，即使语义标签指向其他声音，也先归正常音量” |
| 3 | 已预检的真实喊叫录音（取得使用许可） | 高于门限且语义符合时为大声喧哗 | “真实喊叫另行验证；若未备好合适素材，就不声称已验证” |
| 4 | 已预检的真实游戏外放录音 | 高于门限且语义符合时为游戏外放 | “不能仅靠电子合成音就断言游戏场景验证通过” |
| 5 | `steam_whistle.wav`、钢琴等非目标语义素材 | 高于门限时允许未分类；低于门限为正常音量 | “其他标签或低置信度不会被硬归为正常交谈” |

**门控规则**：每段 `rms_dbfs` ≤ `normal_volume_dbfs`（默认 -45 dBFS）先归正常音量；高于该值才做语义分类。`normal_volume_dbfs` 可配置。dBFS 是数字相对电平，受设备、增益与距离影响，**不是 dB SPL 声压级**，不作为环境分贝测量。

> **历史记录的边界**：旧版曾把 `piano.wav` 判为乐器声约 0.97、`real_speech_0.wav` 判为正常交谈约 0.85、6 条 ESC-50 掌声归为大声喧哗约 0.11～0.93。乐器声类别现已移除，旧版数值不是新版结果；**掌声不是真实喊叫，不能证明喊叫识别能力**。合成样本也只能验证流程，不能冒充真实场景准确率。

**话术**：

> "离线路径完全走内核：UI 只传了个文件路径，音频内容从头到尾没进 UI 进程。"

**加分动作**：当场敲命令证明：

```powershell
.\build\bin\dorm_noise_kernel.exe --offline .\models\ast_audioset.onnx .\assets\audio_demo\real_speech_0.wav
```

## ❓ 评委可能问的问题 & 应答要点

| 问题 | 应答要点 |
|---|---|
| **为什么用 AudioSet 527 类而不是直接训 4 类？** | 正常音量由 RMS 门控先判，其余三类使用 AudioSet 语义映射；其他标签或低置信度保留未分类。语义映射变化须重新生成标签表并重编译，不用重训。 |
| **330 MB 模型是不是太大了？** | 是 AST 微调全量权重（12 层 × 768 hidden）。已实测 int8 动态量化：**330 MB → 91 MB（↓74%），延迟 ≈990 → ≈525 ms/段（1.9×）**，旧版映射下 13 个演示素材的分类与细分标签 13/13 一致；不代表新版四类验收。`scripts/quantize_model.py` 一键产出 `models/ast_audioset_int8.onnx`，内核换 `--model` 即可加载。 |
| **推理延迟？** | 实测均值 **fp32 ≈990 ms/段 · int8 ≈525 ms/段**（i9-14900HX，8 线程自动，CPU EP），远低于 5 秒分段周期，实时性充裕（采集与推理分线程，推理不阻塞采集）。 |
| **怎么验证识别准确？** | 分别准备低电平、真实交谈、真实喊叫、真实游戏外放和非目标声音；记录新版每段 RMS、配置门限、语义标签、分类/未分类结果。旧版钢琴与鼓的乐器声结果不能当新版准确率。 |
| **大声喧哗的样本不好准备怎么办？** | 使用有许可且已预检的真实喊叫录音；没有合适素材就如实说明尚未验证。掌声、音乐、敲桌子或合成音不能替代真实喊叫验证。 |
| **正常音量是环境分贝吗？** | 不是。它表示每段 RMS ≤ 可配置 `normal_volume_dbfs`（默认 -45 dBFS）；是相对数字满刻度的电平，不是经过校准的 dB SPL。低电平优先，高于门限才按语义分类。 |
| **为什么不存音频就"取证"不了，误判了怎么办？** | 这是刻意的隐私权衡（题目要求）。误判可通过调阈值缓解；真正需要留证的场景应该另开授权流程。 |
| **UI 会不会偷偷把音频传出去？** | UI 进程只连 127.0.0.1；`server_name="127.0.0.1"`、`share=False`；协议里根本没有音频字段。可以现场 `netstat` 证明无外连。 |
| **IPC 怎么保证 UI 不把广播当成命令回应？** | 每条命令带唯一 `rid`，内核回填 `rid`；state 广播不带 `rid`。UI 按 `rid` 精确配对（`ui/kernel_client.py` 的 `_pending` 字典），所以 500 ms 一次的周期广播不会挤掉命令响应。 |
| **能不能识别"谁"在说话？** | 不能，也不做。系统只输出「哪一类」，没有声纹、没有 ASR。 |
| **跨平台吗？** | 内核已用 `#ifdef _WIN32` 兼容 Winsock/POSIX socket，Linux 下改 `-DORT_ROOT` 指向 linux 版 SDK 即可。 |
| **代码量 / 复杂度？** | 内核 7 个 .cpp + 8 个 .h，约 2500 行；UI 约 600 行；无第三方 JSON 库（自写 `json.h`）。 |

## 🧰 现场救场预案

| 事故 | 预案 |
|---|---|
| 麦克风没声音 | 立刻切离线推理（第 3 幕），效果等价；或 `Get-ChildItem` 确认系统默认录音设备 |
| 端口 8765 被占 | `netstat -ano \| findstr 8765` → `taskkill /PID <pid> /F`，或 UI 改 `--port 8766` |
| UI 打不开 | `python ui\app.py` 看报错；**Gradio 界面端口**被占时用 `python ui\app.py --ui-port 7861`（内核端口用 `--port 8766`） |
| 内核启动崩溃 | 几乎都是残留进程：`Stop-Process -Name dorm_noise_kernel -Force` 后重试 |
| 模型加载慢 | 第一次加载约 3～5 秒（330 MB），提前启动内核让它预热 |
| 现场断网 | **完全不受影响** —— 模型和音频都在本地，推理全离线 |
| 投影仪分辨率怪 | 浏览器按 F11 全屏；UI 是响应式布局，1920×1080 下正常 |
